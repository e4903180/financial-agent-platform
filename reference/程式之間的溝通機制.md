在這樣一個解耦的企業級架構中，系統的運作可以被切分為兩個完全獨立的生命週期：**「離線模型微調（Maturity/CI）」**與**「線上即時推理（Runtime）」**。

以下為你拆解這兩個系統的進入點、程式之間的溝通機制（Data Flow）以及叫用細節。

---

## 1. 離線微調管線（Train Pipeline）

這個流程通常由 MLOps 工程師手動觸發，或由 CI/CD 工具（如 GitHub Actions、Azure DevOps）在資料更新時定期排程發動。

```
[ 地端/CI 終端機 ] ──執行(1)──► [ src/train/submit_aml_job.py ]
                                         │
                                   (2) 提交 SDK 請求
                                         ▼
                                 [ Azure ML 雲端算力 ] ──執行(3)──► [ src/train/train_entrypoint.py ]
                                                                             │
                                                                       (4) 載入超參數
                                                                             ▼
                                                                  [ config/llama_factory_config.yaml ]

```

### 🏁 進入點

* **本地進入點：** src/train/submit_aml_job.py
這是你或自動化排程在地端（或 CI 伺服器）執行的腳本。
* **雲端進入點：** src/train/train_entrypoint.py
這是當 Azure ML 算力叢集（如 A100 節點）啟動並建立好 Docker 環境後，在雲端虛擬機內真正執行的第一個程式（入口）。

### 🔄 叫用與溝通細節

1. **環境與設定載入：** submit_aml_job.py 透過 Azure ML Python SDK 驗證企業身分，讀取 config/llama_factory_config.yaml 中定義的微調超參數（如 Learning Rate、Rank, Alpha 等）。
2. **派送雲端任務：** 該腳本將 src/ 底下的程式碼包裝成快照，連同設定檔一起提交給 Azure ML，指定在雲端算力上執行命令：
```bash
python src/train/train_entrypoint.py --config config/llama_factory_config.yaml


```



```
3.  **雲端內部溝通：** train_entrypoint.py 在 A100 上啟動後，會讀取傳入的 yaml 檔，調用內部下載好的訓練資料（data/training/），並啟動微調框架（如 LLaMA-Factory）開始訓練。
4.  **產出與儲存：** 訓練結束後，程式透過 API 將僅數百 MB 的 LoRA 權重上傳至企業私有模型庫（Hugging Face Private Registry），隨即自動關閉雲端虛擬機停止計費。

## 2. 線上即時推理管線（Runtime Agent API）

這是服務上線後的常駐流程，負責處理使用者的即時金融查詢。


```

[ 前端 UI / 網頁 ] ──(1) HTTP POST──► [ src/agent/router.py (進入點) ]
│
(2) 叫用並取得 LLM 實例
▼
[ src/agent/model_factory.py ]
│
┌──────────────┴──────────────┐
▼ (依意圖選擇工具)             ▼
[ src/agent/tools/sql_tool.py ]   [ src/agent/tools/rag_tool.py ]
│                             │
(3) 呼叫底層驅動               (3) 呼叫底層驅動
▼                             ▼
[ src/database/azure_sql.py ]     [ src/database/ai_search.py ]

```

### 🏁 進入點
*   **系統應用進入點：** src/agent/router.py
    無論你是用 FastAPI 還是 LangServe 包裝，使用者的問題（User Query）進入後端後，第一個接手處理的程式就是 router.py 中的意圖判斷邏輯。

### 🔄 叫用與溝通細節（以私有 LoRA 模型查詢為例）

#### 步驟一：意圖路由與模型初始化（Router ──► Model Factory）
1.  router.py 收到使用者的問題（例如：「幫我查 2025 年 A 公司的毛利率」）。
2.  router.py 分析問題後，判定這是一個需要高精準度、涉及內部資料庫的**結構化查詢**。
3.  router.py 叫用 model_factory.py 的靜態方法：
    ```python
    # 叫用模型工廠，指定切換為私有微調過的 LoRA 模型
    llm_instance = ModelFactory.get_model(provider="private_lora", model_name="Llama-3-8B-Instruct")
    

```

4. model_factory.py 回傳一個已經設定好目標 vLLM 伺服器端點、並在請求標頭（Headers）中帶有 lora_name: "taiwan_finance_sql_adapter" 的 LangChain ChatOpenAI 實例。

#### 步驟二：驅動特化工具（Router ──► SQL Tool）

1. router.py 將取得的 llm_instance 與定義在 config/agent_config.yaml 中的金融 System Prompt 綁定，組裝成 LangChain 鏈（LCEL）。
2. 因為判定是結構化數據，LangChain 鏈會動態叫用（Invoke） src/agent/tools/sql_tool.py。

#### 步驟三：基礎設施執行與安全稽核（SQL Tool ──► Azure SQL Driver）

1. sql_tool.py 將模型初步生成的 T-SQL 語句傳給 src/database/azure_sql.py。
2. azure_sql.py 負責與 Azure SQL Database 建立連線池。在正式送出查詢前，它會執行一段嚴格的 Regex 稽核程式（**安全防線**），檢查語句中是否包含 DROP、ALTER 或 DELETE 等危險關鍵字。
3. 確認安全無虞後，azure_sql.py 將 SQL 送入資料庫，並將傳回的結構化表格數據（Dataframe/JSON）回傳給 sql_tool.py。

#### 步驟四：最終生成與回應

1. sql_tool.py 將乾淨的數據交回給大模型實例。
2. 模型依據 src/agent/prompts.py 裡指定的「PwC 金融顧問人格」，將冰冷的數字轉化為格式優雅、帶有繁體中文商業口吻的 Markdown 報告，最後透過 HTTP 回傳給前端網頁呈現給使用者。

## 3. 各模組間的「溝通協定（Data Protocol）」

為了確保這些程式互相叫用時不會出錯，資料傳遞遵循標準格式：

* **Config ──► 程式：** 統一使用標準的 Python yaml 或 json 函式庫讀取，將設定轉為字典（dict）。
* **Router ──► Model Factory：** 透過強型別參數（或 Pydantic Model）傳遞 provider_name 與 temperature。
* **Database ──► Agent Tool：** 結構化數據統一轉為 List[Dict]（即 JSON 陣列）或 Markdown 格式的 String，確保 LLM 能夠直接閱讀。非結構化文本則包裝成 LangChain 的 Document 物件（內含 page_content 文本與 metadata 來源標籤）。
